# T3 Code integration

AGS runs one persistent T3 environment per Git repository. Its main checkout and
linked worktrees share one container and one saved SSH connection in T3 desktop.
The desktop connects through a genuine host-side SSH bridge; commands and local
port forwarding execute inside the repository's container.

## Install and connect

```bash
ags tools --packages config/tool-packages.example.json
ags update-image
ags update-agents
ags --agent t3
```

In the tool picker, press `a` and select T3 plus the providers you intend to use.
T3 does not select its backing providers automatically. AGS installs npm package
`t3` through pnpm, using the same release-age, disabled-install-script, candidate
verification, and immutable-generation policies as Pi.

Run registration interactively from the main checkout or a linked worktree.
AGS uses Git's common-directory identity to find the main checkout and records
the selected global config and the main checkout's trusted `.ags/config.toml`.
Use `--config PATH` on this initial invocation for an alternate global config.
The initial launch options become that repository's registered settings;
conflicting settings are reported rather than creating a second environment.

AGS prints an alias such as `ags-t3-0123456789abcdef`. Add this alias as an SSH
environment in T3 desktop. AGS writes the managed SSH entry under its T3 data
directory and adds an `Include` to `~/.ssh/config`, preserving existing content.
The alias invokes AGS through `ProxyCommand`, including when the container is
stopped. Multiple repository environments can appear in the same desktop UI.

Use the alias on the same host where AGS registered it. Leave the port at its
default (22) and use the managed `dev` user/key from the SSH configuration. There
is no listening host SSH TCP port: `ProxyCommand` carries SSH over a private local
Unix socket. Startup prints the transport explanation and managed config path.
Inspect OpenSSH's resolved settings with `ssh -G ags-t3-0123456789abcdef`.
Container port 3773 is the T3 application server, not an SSH port.

The SSH bridge recognizes the v0.0.45 desktop bootstrap contract. It reads the
launch/pairing operation, release runtime layout, and requested version rather
than requiring the desktop's entire installer script to match byte-for-byte.
Helper serialization, installer changes, indentation, and line endings do not
change those operations. It does not execute incoming installer scripts.
Forwarding targets only the T3 server on container loopback port 3773. The relay uses the image's
fixed Node runtime, so T3 forwarding works with `extra_dnf_packages = []` and
does not require selecting `socat`.

## Choosing folders

The desktop's folder picker and path autocomplete browse the T3 server's
container filesystem. AGS initializes T3's `addProjectBaseDirectory` setting to
the registered main checkout, so choosing a local folder starts in the mounted
repository rather than the isolated T3 application home. An existing non-empty
picker setting is preserved. The server's working directory is also explicitly
set to the main checkout.

Checkout and worktree paths retain their identical absolute host/container
locations. T3-created worktrees remain under the persistent `.t3/worktrees`
directory; existing external worktrees are mounted individually. For an existing
environment created by an older AGS build, install the updated AGS binary and run
`ags t3 upgrade`, select the affected environments, then reconnect the desktop
to load the picker setting. A stopped environment can be upgraded directly by ID.

## Lifetime and management

```bash
ags t3 status
ags t3 upgrade                       # unchecked list of working environments
ags t3 stop                          # choose working environments to stop
ags t3 upgrade ags-t3-0123456789abcdef # ID copied from status
ags t3 stop ags-t3-0123456789abcdef
ags t3 status --repository /absolute/path/to/a/worktree
ags t3 upgrade --all                  # explicit non-interactive bulk opt-in
ags t3 --help
ags t3 upgrade --help
```

`ags t3 --help` shows T3 management help; each action also supports `--help`.

- `status` lists **all registrations from any directory** as a JSON array. Each
  entry includes `environment` (the stable SSH alias), full `repository_id`,
  repository path, owner PID/availability, server/container state, runtime
  generation, and diagnostic location. `state` is `running`, `stopped`, or
  `unavailable`; unavailable entries include `error`. Errors do not hide other
  registrations, but status exits nonzero if any entry is unavailable. An empty
  registry returns `[]` without creating T3 storage or starting services.
- `stop` explicitly stops T3 and the repository container. Mounted state and
  the stopped container remain available for a later start. The host owner keeps
  its control endpoint so delayed desktop teardown does not restart the environment.
- `upgrade` stops and recreates the container with the current configured image
  and runtime generation, and restarts its owner with the current AGS executable
  so SSH compatibility fixes take effect. Mounted state survives; the unmounted
  writable layer can be replaced. This operation stops active jobs.

Upgrade first reacquires any registered `--env` values from the invoking shell or
configured secret sources. Missing values are reported by name before the current
owner/server is stopped. Export transient launch values before upgrading, or
configure a reacquirable source; AGS stores only their names in the registration.
Owner-reported stop failures and timeouts propagate to the caller. Direct
container-stop fallback is used only when the owner endpoint is absent/refused.

Without a selector, `stop` and `upgrade` show a scrolling checkbox list of working
instances, including their IDs, repository paths, SSH aliases, and runtime
versions. **Every checkbox starts unchecked.** Use Up/Down (or j/k) to move,
Space to toggle, and Enter to act on the selection. Escape, Ctrl-C, and submitting
an empty selection leave all environments unchanged. The terminal is restored
before any action runs.

Working instances have valid registrations/metadata, a responsive owner reporting
a running server, and a running owned container. Stopped and unavailable instances
remain visible in status but are excluded from global selection and `--all`.
Selected environments are rechecked before acting; an instance stopped while
the checklist was open is reported as a failure and is not restarted.

Supply the displayed `environment` ID (or the full `repository_id`) to act on one
environment without prompting. `--repository PATH` remains an explicit selector
for a main checkout or linked worktree. Targeted status returns one JSON object;
targeted upgrade also supports stopped environments and recovery. These selectors
are independent of the command's working directory and cannot be combined.

For automation, `stop --all` and `upgrade --all` explicitly select every working
instance without prompting. A global action with eligible instances requires
interactive stdin/stderr unless `--all` or a single-environment selector is given.
Actions execute sequentially with a per-environment result and final summary;
failures do not prevent later selected environments from being processed, and
any selected failure makes the command exit nonzero. All bulk upgrades use each
environment's registered configuration.

Desktop disconnect closes its SSH transport while the environment and jobs
continue. A long-lived AGS owner retains applicable host sidecars and runtime
leases. Cold reconnection starts that owner automatically. Recovery reconciles
an ownerless container and the old owner's host process group before admitting
new work. Container reuse/removal validates repository ownership, host UID,
registration, image, and bind-mount metadata.

`update-agents` publishes generations without switching existing environments.
Ordinary reconnect and stop/start retain the existing image and generation;
adoption is explicit through `upgrade`. Disabling T3 rejects new bootstrap,
pairing, and forwarding work. Existing jobs continue until explicit stop.

Browser-enabled cold starts can recreate a stopped container when its persisted
proxy command targets the previous browser's host port. This refresh retains the
same pinned image/runtime and mounted data; it does not adopt a newer generation.
The unmounted writable layer is replaced when this recreation is needed.

Persistent T3 launch supports the registered browser, host UI, clipboard, auth,
webview relay, and optional PSP integrations. It uses `ags --agent t3` without
`--tmux`, `--stop-when-done`, `--lockdown`, or arbitrary CLI passthrough.
Runtime inspection remains available with `ags --agent t3 -- --version` or
`ags --agent t3 -- --help`.

## Storage and provider homes

The default data root is `~/.local/share/ags/t3`, or `$XDG_DATA_HOME/ags/t3`.

| Location under the data root | Purpose |
| --- | --- |
| `registry/<repository-id>.json` | Non-secret registration and configuration context |
| `identity/<repository-id>/` | Host-only SSH identity, environment metadata, diagnostics, and bootstrap assets |
| `ssh/<repository-id>.conf` | Managed OpenSSH alias |
| `environments/<repository-id>/home/` | Persistent T3 home, mounted at its identical absolute host/container path |

Within the T3 home, `.t3/userdata`, `.t3/worktrees`, and `.t3/ssh-launch` are
writable persistent application data. `.t3/runtime` is a read-only bind of the
generation-owned compatibility bundle in `pnpm-home/ags-t3-runtime`. The
installed launcher, platform package, native dependencies, client assets,
resource monitor, completion marker, and runtime view participate in inventory.

T3-supported enabled providers use AGS-managed wrappers. Codex, Claude, and
OpenCode retain the existing `/home/dev` provider configuration and shared
authentication/history mounts. Wrappers preserve applicable AGS hooks and
sandbox instructions while leaving T3's provider permission selection in charge.
Host SSH keys and lifecycle control are outside sandbox mounts; AGS rejects
mount layouts that would expose those private locations.

## Worktrees

The checkout, required external Git metadata, and existing relevant worktrees
are mounted at identical absolute host/container paths. T3's default new
worktrees live below its persistent `.t3/worktrees` parent, already mounted
before creation. Host Git and editors can use those checkouts directly.

An external worktree created outside the mounted layout requires explicit
`ags t3 upgrade`. AGS reports this instead of silently interrupting active jobs.
General worktree-aware Node version discovery is deferred to
[GitHub issue #23](https://github.com/thomaspeklak/agent-sandbox/issues/23): the existing Node
wrappers use the registered main workspace boundary, while T3's npm launcher
uses the fixed image Node bootstrap.

## Version policy and credentials

T3 desktop requests an exact runtime version before server reuse, including
during pairing. AGS checks the requested, mounted, and running versions and
rejects mismatches before any installer/download can execute. Use a matching
desktop, or explicitly update agents and recreate the environment. The pnpm
release-age policy can make the newest desktop newer than the selected runtime.

Runtime installation belongs to `update-agents`. Its fresh verification
container mounts runtime files read-only with `--network=none`, starts the
server, pairs, verifies filesystem browsing and directory-prefix autocomplete,
and exercises native PTY open/write/resize/close before publication.

Fresh server boots resolve configured credentials on the host and pass them
through anonymous sealed descriptors. Resolved values are absent from durable
registration, Podman container configuration, and command arguments. Registered
`--env` values are reacquired from the owner's environment or configured secret
sources; only their names are persisted. Explicit 1Password sources retain the
existing Secure Note bootstrap and override precedence, with bounded
noninteractive lookup. Prepare passphrase/unlock prerequisites interactively;
SSH protocol bytes are never used for prompts.
